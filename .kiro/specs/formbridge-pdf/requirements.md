# FormBridge PDF — Requirements

**Spec:** formbridge-pdf  
**Target:** deployed and passing acceptance scenario by 2026-11-17  
**Part of:** ReForge AI (Kiroween 2026, Frankenstein category)

---

## Overview

FormBridge is the PDF form-assistance module of ReForge AI. A user selects their preferred language, uploads an AcroForm PDF, and the app guides them through each form field one question at a time in that language. Answers are validated as they go. At the end, the user reviews every answer, edits if needed, confirms, and downloads the filled PDF.

Three settings are kept strictly separate:
- **Interface language** — the language the user reads questions and instructions in.
- **Form output language** — the language the form expects answers in, detected from the PDF during analysis with a confidence check; the user is asked to confirm when confidence is uncertain.
- **Form country** — determines which country pack handles field validation (IC, phone, postcode, etc.), detected from the form and confirmed by the user when uncertain.

ReForge AI is a global product for people completing essential forms across a language barrier — international migrants, refugees, older adults, and travellers. Malaysia is the first deployment and case study; the architecture is built to travel.

**What is sent to the AI service:** before the first analysis request, the app shows the user a summary of what will be sent — the field names, tooltips, nearby label text from the PDF, and any description-field text the user explicitly chooses to translate — and asks them to continue. User answers stay in the browser, except that a description answer the user explicitly asks to translate is sent once for translation and is not stored or logged. The PDF binary stays in the browser.

**Demo story:** "Read the questions in your language, fill the form in the language it requires."
- Nov 17 main demo: Chinese (`zh-Hans`) interface → Malay-language Malaysian clinic form.
- Dec 1 second demo: Spanish (`es`) interface → English-language US community clinic form.

## Requirements

### 1. Supported PDF types and rejection

**1.1** Accept fillable AcroForm PDFs with text fields, checkboxes, radio groups, and dropdown (choice) fields.

**1.2** Enforce hard limits before analysis: maximum 10 MB file size, 20 pages, and 150 form fields.

**1.3** Detect and reject the following cases with a clear error message in the user's chosen language (which is already selected before upload — see 2-L.8). Never crash on a bad file; all rejection paths must be handled gracefully:
- XFA forms: detected by the presence of a populated `/XFA` entry in the AcroForm dictionary.
- Encrypted or password-protected PDFs.
- Digitally signed PDFs: detected by the presence of a `/Sig` field widget that has a value (i.e. the signature is populated). An empty `/Sig` field is not a signed document and must not be rejected — it is shown as "fill this yourself" in the review (see 5.3).
- PDFs with no interactive form fields (e.g. scanned images).
- Files that exceed any of the limits in 1.2.
- Files that are not valid PDFs.

**1.4** Error messages for rejection cases must be available in all languages with translation status `core` in the language registry (see Requirement 2-L) and rendered before any AI call is made. Languages with status `experimental` fall back to English for rejection messages until their locale file is complete. Because the language is chosen before upload, the correct locale is always available at rejection time.

---

### 2. Language registry

**2-L.1** The set of supported languages is defined by a language registry — a single module containing an array of entries. Adding a new language means adding one locale file and one registry entry; no other code changes are required. Missing UI string keys for a language fall back to English.

**2-L.2** Each registry entry contains:
- BCP 47 tag (e.g. `zh-Hans`)
- Native name (e.g. `简体中文`)
- Text direction (`ltr` or `rtl`)
- Font family (Noto family for the script)
- Translation status: `core` or `experimental`
- Model language name (used in AI prompts)

**2-L.3** Fonts are loaded per script only when that language is selected by the user.

**2-L.4** CSS logical properties (`inline-start`, `block-start`, etc.) are used from the start, so RTL layout is low-cost to enable. RTL languages are only declared supported after RTL rendering, mixed-direction numbers, punctuation, and keyboard order have been tested.

**2-L.5** Languages by target date:

| Status | BCP 47 tags | Target |
|--------|-------------|--------|
| `core` | `en`, `ms`, `zh-Hans`, `zh-Hant`, `ta`, `es` | Nov 17 |
| `experimental` | `id` | Nov 17 |
| `experimental` | `bn`, `ne`, `my`, `hi`, `vi`, `th`, `tl`, `ja`, `ko`, `ar`, `ur`, `fr`, `pt`, `ru` | Dec 1 |

**2-L.6** Every question and translation generated by the AI is labelled as machine-translated, in every language.

**2-L.7** Next to every AI-generated question, show the original label from the PDF (tooltip if present, otherwise the nearby text snippet). Do not fabricate an "original English label" when the PDF only has a meaningless internal name such as `Text1`.

**2-L.8** The language picker is the first screen the user sees, before the upload screen. The picker pre-selects the language that matches the user's browser language setting; if the browser language is not in the registry, it defaults to English. The chosen language is active for the upload screen, all rejection messages, the data-disclosure notice, and every subsequent screen.

---

### 3. Country pack registry

**3-C.1** Country-specific field validation is delivered through pluggable country packs. A single country pack registry (same pattern as the language registry) maps an ISO 3166-1 alpha-2 country code to its validation rules. Adding a country means adding one pack module and one registry entry; no other code changes are required.

**3-C.2** Country packs by target date:

| Pack | Target | Contents |
|------|--------|----------|
| `MY` | Nov 17 | Malaysian IC (MyKad / NRIC), Malaysian phone numbers, 5-digit postcode (see §7.1–7.3) |
| `US` | Dec 1 | US phone numbers, ZIP and ZIP+4, MM/DD/YYYY date format, SSN format check only (never claim verification; SSN is never sent to the backend) |
| `universal` | Nov 17 | International phone numbers via `libphonenumber-js` (needs a country hint), email, dates with explicit format confirmation, permissive postcodes (unfamiliar formats kept as typed). Permissive fallback; not full validation. |

**3-C.3** The form country is detected from the form during analysis and returned alongside the form output language. When confidence is below a threshold, the user is asked to confirm the country before question-answering begins.

**3-C.4** The UI and README list tested country packs explicitly and mark unvalidated countries as experimental. The app never claims to support "any form in any country".

### 4. Field extraction and identity

**4.1** For each form field, extract the following evidence from the PDF without sending user answers to the backend:
- Field name (internal PDF name, e.g. `Text1`)
- Tooltip / alternate description
- Field type (`text`, `checkbox`, `radio`, `dropdown`, `signature`)
- For dropdowns and radio groups: the list of allowed option values from the PDF itself
- Required flag and read-only flag
- For `/Sig` fields: whether the field has a value (populated) or is empty
- Max length for text fields
- Page number and approximate bounding box (left, top, right, bottom in user-space units)
- A page text snippet: the nearest ~200 characters of text on the same page, positioned around the field's bounding box, extracted via pdf.js

**4.2** Multiple widgets sharing the same internal field name are treated as a single logical field (radio group model).

**4.3** Read-only fields are included in the review screen but are never presented as questions to the user.

**4.4** Any existing value already written into the PDF is not sent to the backend and is not displayed as a suggested answer.

**4.5** Page text snippets are capped at ~200 characters and must be treated as untrusted data throughout the pipeline — never interpolated into AI prompts as instructions.

---

### 5. AI-powered form understanding

**5.1** After extraction and after the user has acknowledged the data-disclosure notice (Overview), send the field evidence to the backend. The request also includes the detected form language (or, if ambiguous, the user-confirmed output language) and detected country. For forms up to a bounded field count (to be set in design), this is a single request. For larger forms, split into batches so that each batch has a bounded number of fields and bounded output tokens. A truncated or missing reply for any batch is treated as "fill this yourself" for the fields in that batch.

**5.2** The maximum number of retries is one retry per batch. The total is therefore at most one request plus one retry per batch.

**5.3** The backend detects the form's output language and country during analysis and returns each with a confidence value. When either confidence is below a threshold, the response includes a flag and the app asks the user to confirm before question-answering begins.

**5.3a** Form output language support is delivered in phases:
- **Nov 17 (fully tested, main demo path):** English and Malay forms (Latin script).
- **Dec 1:** Chinese forms (`zh-Hans`, `zh-Hant`), enabled by embedding a subsetted Noto CJK font using `@pdf-lib/fontkit`. A model comparison spike (Spike 1) and a CJK font embedding spike (Spike 2) are the first two tasks in tasks.md. CJK feature tasks are only scheduled if Spike 2 passes.
- **Later, experimental only:** Tamil forms — pdf-lib does not fully shape complex scripts; Tamil stays marked experimental until a native reader and viewer check confirms correct rendering.
- **Out of scope for this spec:** RTL PDF output (Arabic, Urdu). RTL interface support is a separate concern covered by the language registry.

**5.4** The backend returns, for each field in the submitted list:
- `fieldId`: the internal PDF field name
- `humanLabel`: a short, readable label in the user's chosen language
- `question`: a plain-language question for the user in the user's chosen language
- `answerType`: one of `text`, `ic`, `phone`, `postcode`, `date`, `email`, `checkbox`, `radio`, `dropdown`, `description`, `signature`
- `confidence`: a number from 0.0 to 1.0

**5.5** Validate the AI response with a zod schema. Reject any entry where `fieldId` was not in the submitted field list. Reject duplicate `fieldId` entries (keep the first, discard the rest and log a warning). Fields in the submitted list that are absent from the AI reply are treated as "fill this yourself".

**5.5a** After schema validation, check every AI-assigned `answerType` against the PDF's own field type:
- A PDF `checkbox` field: `answerType` must be `checkbox`.
- A PDF `radio` group: `answerType` must be `radio`.
- A PDF `dropdown` field: `answerType` must be `dropdown`.
- A PDF `signature` field: `answerType` must be `signature`.
- A PDF `text` field: `answerType` may be any of `text`, `ic`, `phone`, `postcode`, `date`, `email`, `description`; it may not be `checkbox`, `radio`, `dropdown`, or `signature`.

An `answerType` that violates these rules is replaced with the PDF's own field type and `confidence` is set to 0. PDF flags (required, read-only, signature populated/empty) always win over AI assignments.

**5.6** If a batch response fails schema validation, retry that batch once with the same input. If it fails again, fall back: use the raw field name or tooltip as the label; preserve the PDF's own field type for checkboxes, radio groups, dropdowns, and signature fields; only text fields fall back to `answerType: text`. Set `confidence` to 0.

**5.7** A confidence value below 0.7 is treated as low confidence (see Requirement 6).

**5.8** Cache the analysis result for the browser session, keyed by the file's content hash. Switching the display language re-uses the cached structural analysis and only re-translates the `question` and `humanLabel` strings; no new AI call for field structure is made.

**5.9** The user may override the `answerType` that the AI assigned to any field. The override must be compatible with the PDF's underlying field type.

**5.10** All PDF text passed to the backend must be tagged in the AI system prompt so the model is explicitly instructed to treat it as form data, never as instructions.

### 6. Low-confidence and unresolvable fields

**6.1** When a field's confidence is below 0.7, the question screen for that field shows:
- The original field label (name or tooltip) without fabrication
- The page text snippet for context
- A prompt asking the user to confirm or edit the generated question before answering

**6.2** A field that remains unresolvable after the AI fallback (confidence 0, no tooltip, no usable page snippet) is listed as "fill this yourself" with its page number and approximate location in the PDF.

**6.3** Empty `/Sig` signature fields are always listed as "fill this yourself — sign after printing" and are never asked about or written to.

**6.4** A field with status "fill this yourself" is shown on the review screen with that status. It is never silently dropped and no value is guessed for it.

### 7. Validation (deterministic, runs in the browser)

All validation messages are displayed in the user's chosen language. Validation rules are provided by the active country pack (§3-C).

**7.1 `MY` pack — Malaysian IC (MyKad / NRIC)**
- Accept input with or without dashes.
- Normalize to 12 digits (remove dashes and spaces).
- Validate the first 6 digits as a date in YYMMDD format:
  - Attempt to parse as 20YYMMDD first; if the resulting date is valid and not later than today's date, accept it.
  - Otherwise attempt to parse as 19YYMMDD; if valid, accept it.
  - If neither parses as a valid calendar date, reject with a clear message.
- Validate digits 7–8 as a birthplace code. The full list of valid state and overseas codes is stored as a single named constant (`MY_IC_BIRTHPLACE_CODES`) with a comment citing the source URL from the official JPN (Jabatan Pendaftaran Negara) documentation.
- Reject if digits 7–8 are not in the birthplace code list.
- The app does not infer or display the user's age or birth year from the IC number.
- The app does not claim the IC number is verified as real; the validation comment explicitly states there is no checksum.

**7.2 `MY` pack — Malaysian phone numbers**
- Build a prefix and length table from the official Malaysian Communications and Multimedia Commission (MCMC) numbering plan (cite the source URL in a comment). The table must cover:
  - Mobile prefixes and their exact subscriber digit lengths, including `011` (8 subscriber digits) and all other `01x` prefixes (7 subscriber digits, as applicable).
  - Landline area codes, which vary in length: `03` (Klang Valley), `04`–`09` (other states), and `082`–`089` (Sabah/Sarawak).
- Accept the `+60` and `60` country-code prefixes in addition to the leading-zero form.
- Validate that the number matches a known prefix and has the correct total subscriber digit count for that prefix.
- Reject numbers that do not match any known prefix-length combination.
- Write the number in the standard grouping for its type (e.g. mobile `011-XXXX XXXX`, landline `03-XXXX XXXX`).

**7.3 `MY` pack — Postcode**
- Accept exactly 5 ASCII digits. Reject anything else.

**7.4 `US` pack — Phone, ZIP, date, SSN**
- Phone: validate US phone numbers (NANP format); accept `+1` prefix.
- ZIP: accept 5-digit ZIP and ZIP+4 (NNNNN or NNNNN-NNNN).
- Date: use MM/DD/YYYY as the output format for US forms.
- SSN: perform format check only (NNN-NN-NNNN); never claim verification; never send to the backend.

**7.5 Date (all packs)**
- Accept DD/MM/YYYY and YYYY-MM-DD as input; US pack also accepts MM/DD/YYYY.
- Choose the output format from an explicit date pattern in the field tooltip or nearby page text. If the pattern is ambiguous or absent, ask the user to confirm the output format before proceeding.
- Reject invalid calendar dates.
- After formatting, check the result against the field's `MaxLen` and reject if it exceeds it.

**7.6 Email (all packs)**
- Validate against standard email format rules.

**7.7 Required fields (all packs)**
- A required field (as flagged in the PDF) must not be left blank. The user may explicitly mark it as "skip" with a visible warning on the review screen.

**7.8 Dropdown and radio values (all packs)**
- Only values present in the PDF's own option list are accepted. The PDF's exact option string is always the value written into the PDF, regardless of how it was displayed to the user in the interface language.

**7.9 Max length (all packs)**
- Reject (with a message) any text answer that exceeds the field's `MaxLen` attribute. Never silently truncate.

### 8. PDF output values

**8.1** Keep the raw user answer (as typed) and the normalized output value (what gets written into the PDF) as separate fields in the application state throughout the session.

**8.2** Names, addresses, and identifiers are written exactly as the user's official documents spell them and are never translated automatically. If the form's script differs from what the user typed, ask the user for the spelling that should go on the form.

**8.3** IC numbers are written in their 12-digit normalized form (no dashes).

**8.4** Phone numbers are written in their normalized, standard-grouped form.

**8.5** For a checkbox: "checked", "unchecked", and "skipped" are three distinct states. An unchecked checkbox and a skipped checkbox are written differently (unchecked writes the PDF false value; skipped leaves the field at its original state).

**8.6** For free-text description fields only: if the user types their answer in a language other than the form's output language, the app offers a translation into the form's output language generated by the backend. The translation is labelled as machine-translated. The user must read, approve, or edit this translation; it is never written to the PDF without explicit user approval.

**8.7** Before writing any text to a PDF field, check that every character is representable in the font that will be used for that field's appearance. If any character is not representable, block the write and display a clear error message in the user's language. Never produce a PDF with blank boxes where characters should be.

---

### 9. Review screen and consent

**9.1** Before any download, show a review screen that lists every form field with:
- Original field label (from the PDF — tooltip or, if absent, the nearby page snippet; never fabricated)
- The question that was asked
- The answer that will be written into the PDF (the normalized output value)
- Status: `filled`, `skipped`, or `fill yourself`

**9.2** The review screen is implemented as semantic, accessible HTML (not a canvas-only preview). It is fully keyboard-navigable and screen-reader-friendly.

**9.3** The user can edit any answer from the review screen and re-validate before confirming.

**9.4** The download is only triggered after explicit user confirmation ("Confirm and download PDF").

**9.5** The app never transmits the completed or partially completed form to any external organization. The following notice appears visibly on the upload screen and again on the review screen:

> "Your answers stay in your browser. The form field labels, tooltips, and nearby text from the PDF — and any description answer you choose to translate — are sent to the AI service for processing. Answers are not stored."

---

### 10. PDF filling and output

**10.1** Fill the PDF using pdf-lib.

**10.2** Generate field appearance streams using the embedded font, passing the font explicitly to the appearance update function. Do not rely on the `NeedAppearances` flag or on the viewer to render values. Enforce a minimum readable font size per field. Detect and report text overflow instead of letting text be silently cut off.

**10.3** Fields the user did not answer (status: `skipped` or `fill yourself`) must retain their original value and visible appearance unchanged. Read-only fields must remain unchanged. Note: saving a PDF changes some bytes; the test property for "unchanged" is that the field value and rendered appearance are the same, not that bytes are identical (see 15.1).

**10.4** The filled PDF is served as a file download from the browser with an appropriate filename.

---

### 11. Data flow and privacy

**11.1** User answers stay in the browser's in-memory session state. They are never sent to the backend, stored in `localStorage`, or logged — with one exception: a description-field answer that the user explicitly asks to translate is sent once to the translation endpoint and is not stored or logged.

**11.2** The backend receives:
- Field evidence (names, types, tooltips, page text snippets) for the analysis endpoint.
- A single free-text description answer when the user explicitly requests a translation of it.

**11.3** The backend does not persist, log, or cache either of the above beyond the life of the HTTP request.

**11.4** Uploaded PDF binary data is processed in the browser only; it is not uploaded to the backend server.

### 12. AI service layer and operational limits

**12.1** The AI provider is accessed only through a single `AiProvider` interface. Swapping providers does not require changes to any caller.

**12.2** The production backend uses **Cloudflare Workers AI** via the Workers AI binding (`env.AI`). No API key appears in the browser or in environment variable files. The model is selected from the active Workers AI model list; do not use models scheduled for retirement. The design phase will measure two candidates — `@cf/google/gemma-4-26b-a4b-it` and `@cf/qwen/qwen3.8-27b` — against the fixtures for JSON validity, omission rate, terminology quality, latency, and neuron cost, and will record the selection rationale.

**12.3** A deterministic mock `AiProvider` is provided and used:
- In all automated tests.
- As the default when the Cloudflare Workers AI binding is not available (e.g. local development without a Workers environment).

**12.4** When the mock provider is active, the UI displays a small, persistent "Demo mode — AI responses are simulated" notice.

**12.5** Every outbound AI call has a request timeout. If the timeout is exceeded the user sees a clear "This is taking too long — please try again" message.

**12.6** Input to the AI endpoint is size-limited. Requests that exceed the limit are rejected with a 400 error before the AI call is made.

**12.7** Rate limiting uses the **Cloudflare Workers rate-limiting binding** (per IP). The daily neuron budget for the free plan is 10,000 neurons, resetting at 00:00 UTC. The app tracks consumed neurons as an estimate. When the budget or rate limit is exhausted:
- For the bundled fixture PDFs (matched by content hash): serve precomputed analysis results and display a visible notice that cached analysis is being used.
- For all other uploaded PDFs: fall back to raw-label mode with a clear notice that AI analysis is unavailable.
- The app must not break or show an unhandled error in either case.

### 13. Accessibility

**13.1** Every screen meets WCAG 2.2 Level AA.

**13.2** The app is fully operable by keyboard alone, in logical tab order, with a visible focus ring on every interactive element.

**13.3** Every input has a visible `<label>` associated with it. Error messages are linked to their field via `aria-describedby` and announced via an `aria-live="polite"` region.

**13.4** The HTML `lang` attribute is set to the correct BCP 47 tag from the language registry for the user's chosen language. Any element whose content is in a different language than the page has its own `lang` attribute.

**13.5** Text contrast meets at least 4.5:1 for body text and 3:1 for large text and UI borders.

**13.6** Color is never the sole means of conveying information (errors also use an icon or text label).

**13.7** Touch targets are at least 24×24 px, ideally 44×44 px.

**13.8** Layout is functional and usable at 360 px viewport width.

**13.9** Text can be zoomed to 200% without loss of content or functionality.

**13.10** The app respects `prefers-reduced-motion`.

**13.11** Automated axe checks run on every main screen as part of the Playwright test suite. A short manual accessibility checklist (keyboard-only run, screen reader pass, 200% zoom) is maintained at `docs/accessibility-checklist.md`. Viewer checks for non-Latin PDF output (verify filled values render correctly in Chromium, Firefox, and Acrobat Reader) are also documented there.

### 15. Tests

**15.1 Property-based tests (Vitest + fast-check)** — each test is annotated with the requirement number it validates:
- Every extracted field from any valid AcroForm is either present in the AI reply (mapped) or classified as "fill this yourself"; no field is silently dropped.
- AI-assigned `answerType` compatibility (req 5.5a): for any combination of PDF field type and AI-assigned `answerType`, the result either passes the compatibility rules or is replaced with the PDF's own type at confidence 0; no incompatible type is ever used.
- IC normalization: all valid IC strings (with and without dashes) normalize to the same 12-digit form.
- IC validation: every valid IC passes; every IC with an impossible date or an invalid birthplace code fails with a message.
- Phone normalization: valid Malaysian mobile and landline numbers (for all prefix types in the table) normalize correctly.
- PDF fill + read-back: filling a set of fields then reading the PDF back returns the same values for every filled field.
- Untouched fields: fields not included in the fill operation have the same value and visible appearance as before. Fields that had no appearance stream before filling must also be checked after regeneration.

**15.2 Playwright end-to-end test — Nov 17 acceptance scenario:**
1. Select Chinese (`zh-Hans`) as the language on the language picker screen.
2. Upload `fixtures/clinic-registration.pdf`.
3. Acknowledge the data-disclosure notice.
4. Confirm Malay as the form output language when prompted.
5. Answer every question, including entering a deliberately wrong IC number (which must be rejected with an error message) and then the correct IC.
6. Reach the review screen and verify all answers are listed.
7. Confirm and download the PDF.
8. Render the downloaded PDF with pdf.js:
   - For text fields: verify each filled answer's text bounding box sits inside the corresponding field's rectangle.
   - For checkboxes, radio groups, and dropdowns: read the field value back from the PDF and verify it matches the expected answer; also take a visual screenshot of the rendered page.
9. Run an axe accessibility check on each screen (language picker, upload/disclosure, question wizard, review, download confirmation).

**15.3 Playwright end-to-end test — Dec 1 acceptance scenario:**
1. Select Spanish (`es`) as the language.
2. Upload `fixtures/us-community-clinic.pdf`.
3. Acknowledge the data-disclosure notice.
4. Confirm English (US) as the form output language and `US` as the country pack when prompted.
5. Answer every question, including entering a deliberately wrong ZIP code (which must be rejected) and then the correct one.
6. Reach the review screen and verify all answers are listed.
7. Confirm and download the PDF.
8. Verify filled values in the downloaded PDF as in 15.2 step 8.

**15.4 Unit tests** for all validation functions in Requirement 7 (IC, phone, postcode, US ZIP, date, email, max length, dropdown/radio constraints).

**15.5** When a fast-check property finds a bug, the shrunk failing case is kept as a named unit test with a comment noting which requirement it caught.

### 16. Out of scope for this spec

- Scanned or OCR-only PDF forms.
- XFA-only forms (rejected at upload).
- Populated digital signatures (rejected at upload).
- RTL PDF output (Arabic, Urdu).
- Tamil PDF output (experimental, pending native-reader check).
- User accounts or saving progress across browser sessions.
- The legacy-website module (Spec 2 and Spec 3).
- A browser extension.
