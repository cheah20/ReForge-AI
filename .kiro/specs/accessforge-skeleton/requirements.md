# Requirements Document

## Introduction

AccessForge is the legacy-website module of ReForge AI. This spec covers its smallest end-to-end walking skeleton: one fictional legacy portal, one registration form on it, and a modern **Mirror** that revives that form. The Mirror asks the user plain-language questions in the interface language, validates the answers with the existing country packs, and operates the original legacy page, which still does the real work and returns its own confirmation.

The legacy portal is our own fictional demonstration site, served by the same Worker under `/legacy/`. It reproduces common patterns of an old public-service portal: table layout, tiny fixed fonts, low contrast, unlabelled inputs, abbreviated labels in neighbouring cells, a hidden consent box, a single ambiguous date box, and a reset button next to submit. It is labelled on every page as a fictional demonstration and never imitates a real agency.

The revival runs as an agent loop with five stages:

1. **Observe**: a deterministic extractor builds a compact Page Model of the legacy form. Entered values never enter the Page Model.
2. **Plan**: the AI service proposes the meaning of each element and a plain-language question. A strict schema rejects anything that does not match the Page Model.
3. **Act**: a fixed set of four validated actions (fill, select, check, click) runs on the legacy page inside a same-origin, script-free iframe.
4. **Verify**: the Mirror reads every value back, compares it with what the user intended, stops on a mismatch, and reads the legacy confirmation page.
5. **Report**: the Mirror shows either a verified completion with the legacy reference number, or a "do this yourself" list.

The user confirms explicitly before the legacy form is submitted. The legacy confirmation page links to the FormBridge clinic PDF flow, so the portal and the PDF form are one journey.

This spec reuses FormBridge parts instead of duplicating them: the Language Registry and locale files, the Country Pack Registry and its validators (`MY` pack for IC, phone and postcode; date validation with an explicit format), the `AiProvider` interface with its real and mock providers, the `AI_MODE` switch (mock by default), the shared zod schemas and error shape, the rate-limiting binding, the "machine-translated" label, the Demo mode banner, and the privacy rules for logs and storage.

Honest scope: AccessForge revives owned, compatible legacy workflows that use server-rendered pages and plain HTML forms. This skeleton supports exactly one portal and one form. It does not claim to work with any website, and it does not claim WCAG conformance beyond what the tests and the manual checklist show.

### Acceptance scenario

The user chooses Simplified Chinese (`zh-Hans`) on the language picker and opens the legacy registration page. The legacy page appears in its original old style. The user presses "Revive this page". The Mirror opens beside the legacy page and asks the registration questions one at a time in Chinese. The user types an IC number with an impossible birth date; the Mirror rejects it with a message in Chinese, and the user corrects it. After each answer, the matching field on the legacy page visibly fills in. The review screen lists every question with the value that will be sent. The user presses the confirm button. The legacy handler accepts the submission and returns a reference number. The Mirror shows the confirmation in Chinese with the reference number, and the user can open the original Malay confirmation text on request. A separate direct submission of the same synthetic data through the legacy form, without the Mirror, produces an identical received-fields summary.

## Glossary

- **ReForge_App**: the ReForge AI web app (React + Vite frontend and Cloudflare Worker in one deployment).
- **Worker**: the Cloudflare Worker that serves the frontend, the API routes and the Legacy_Portal.
- **Legacy_Portal**: the fictional legacy-style website served by the Worker under `/legacy/`, with a home page, a registration page and a confirmation response.
- **Legacy_Form**: the new-patient registration form on the Legacy_Portal registration page.
- **Legacy_Handler**: the Worker code that receives the Legacy_Form submission, validates it, and returns the confirmation response or an error page.
- **Legacy_Field**: one form control in the Legacy_Form (text input, select, radio group, checkbox, submit button or reset button). Radio inputs that share a `name` form one Legacy_Field.
- **Synthetic_Registration**: the fixed set of fictional test answers for the Legacy_Form (a fictional name, an IC number, a date of birth, a gender, a mobile number, a postcode, a reason for visit, and consent). The IC, phone and postcode values match those used in the FormBridge clinic PDF fixture.
- **Reference_Number**: the identifier the Legacy_Handler returns for an accepted submission, in the pattern `SR-DEMO-YYYYMMDD-NNNNNN`, where `YYYYMMDD` is the submission date in UTC and `NNNNNN` is six digits.
- **Received_Fields_Summary**: the list the Legacy_Handler returns on the confirmation response, with one entry per Legacy_Field it received, giving the field name and the value exactly as received, in Legacy_Form document order.
- **Allow_List**: the fixed set of Legacy_Portal paths, HTTP methods and response transitions that the Revival_Frame may load or perform.
- **Revival_Frame**: the same-origin iframe in which the ReForge_App shows the Legacy_Portal. Its sandbox allows same-origin access and form submission and does not allow scripts.
- **Mirror**: the modern, accessible view that the ReForge_App builds from the Legacy_Form and shows next to the Revival_Frame.
- **Agent_Loop** (written "agent loop" in criteria): the five-stage cycle of observe, plan, act, verify and report described in the Introduction, running from the press of "Revive this page" until a result is reported, the user cancels, or a criterion stops it.
- **Review_Screen** (written "review screen" in criteria): the Mirror screen that lists every Legacy_Field with its Intended_Value and status before submission and holds the confirm button.
- **Confirm_Button** (written "confirm button" in criteria): the control on the review screen whose press is the user's explicit confirmation to submit the Legacy_Form.
- **Data_Notice** (written "data notice" in criteria): the Mirror notice described in Requirement 13.7 that tells the user what leaves the browser.
- **Re_Translation_Request** (written "re-translation request" in criteria): the request of Requirement 7.7 that carries existing human labels and questions to the Worker for translation into a new Interface_Language.
- **Smoke_Test**: a test that the developer runs on purpose, outside CI and outside the default test command, either with `AI_MODE` set to `real` or against the deployed public URL of the ReForge_App.
- **Page_Version**: the identifier of the exact sanitized HTML of a Legacy_Portal page, computed as a SHA-256 hash of that HTML.
- **Page_Model**: the compact, deterministic description of the Legacy_Form that the Page_Extractor builds: page path, Page_Version, and for each Legacy_Field an element id, control type, `name`, `id`, associated label text, neighbouring-cell text, option values and option texts, `required` and `maxlength` attributes, document position, and nearby page text.
- **Page_Extractor**: the deterministic browser code that builds the Page_Model from the document in the Revival_Frame.
- **Element_Id**: the identifier the Page_Extractor assigns to each Legacy_Field in the Page_Model. It is derived only from the field's form, control type and `name` (and `value` for a radio option).
- **Page_Plan**: the AI-proposed description of the Legacy_Form: for each Element_Id, a human label and a question in the interface language, an answer type, and a confidence from 0.0 to 1.0.
- **Plan_Validator**: the code that checks a Page_Plan against the shared zod schema and the Page_Model and rejects entries that do not match.
- **Heuristic_Extractor**: the deterministic code that builds a Page_Plan without AI, from the Page_Model alone, when no AI or cached plan is available.
- **Precomputed_Page_Plan**: a schema-validated Page_Plan stored in the repo for one Page_Version and one interface language, written only by a named generation script.
- **Analysis_Mode**: which source produced the Page_Plan in use: `live` (real AI), `mock` (the deterministic mock provider), `cached` (a Precomputed_Page_Plan) or `heuristic` (the Heuristic_Extractor).
- **Action**: one operation that the Executor performs on a Legacy_Field. The only Action kinds are `fill`, `select`, `check` and `click`.
- **Executor**: the browser code that performs Actions on the document in the Revival_Frame.
- **Verifier**: the browser code that reads Legacy_Field values back from the Revival_Frame and reads the confirmation response.
- **Intended_Value**: the value the Mirror plans to write into a Legacy_Field after validation and any Documented_Transformation.
- **Documented_Transformation**: a change between the answer the user gives in the Mirror and the Intended_Value, listed by name in the design (for example, joining separate day, month and year answers into the date format the Legacy_Form states).
- **Do_It_Yourself**: the status of a Legacy_Field that the Mirror cannot map or operate reliably. The Mirror lists the field and the user completes it directly in the Revival_Frame.
- **Language_Registry**: the existing FormBridge registry of interface languages and locale files.
- **Country_Pack**: the existing FormBridge validation packs (`MY`, `US`, `universal`), chosen through the Country Pack Registry.
- **AiProvider**: the existing single AI provider interface with the real Workers AI provider and the deterministic mock provider.
- **Interface_Language**: the language the user reads the Mirror in, chosen on the language picker.

## Requirements

### Requirement 1: Fictional legacy portal

**User Story:** As a judge or demo viewer, I want a realistic old-style portal that belongs to the project, so that the revival can be shown end to end without touching any real website.

#### Acceptance Criteria

1. THE Worker SHALL serve under `/legacy/` exactly these Legacy_Portal documents: a home page for GET `/legacy/`, a registration page for GET `/legacy/register`, and the confirmation response or error page that the Legacy_Handler returns for POST `/legacy/register`.
2. THE Legacy_Portal SHALL show a banner as the first visible element of every document listed in criteria 1.1 and 1.10. The banner SHALL state in Malay and in English that the portal is a fictional demonstration and not a real service.
3. THE Legacy_Portal SHALL use only invented personal names, organisation names, addresses, phone numbers and identifiers. It SHALL contain no name, logo, emblem, coat of arms or domain name of a real government agency, clinic or company. It SHALL use only images and fonts that the project owns or that carry a licence allowing use, and the README SHALL list each such asset with its licence.
4. THE Legacy_Portal home page SHALL offer a navigation menu with exactly five top-level entries. The last entry SHALL be a general "others" entry, and the link to `/legacy/register` SHALL be nested inside it. Each of the other four entries SHALL be either plain text or a link to `/legacy/`, so that no menu entry leads to a path outside criterion 1.1.
5. THE Legacy_Portal registration page SHALL contain exactly one form, the Legacy_Form. The Legacy_Form SHALL contain eight Legacy_Fields in this document order: full name, IC number, date of birth, gender, mobile phone number, postcode, reason for visit and consent. These SHALL be followed by one submit button and one reset button. Each Legacy_Field SHALL have a `name` that no other Legacy_Field uses. Gender SHALL be a radio group, consent a checkbox and date of birth a text input. Every text input SHALL carry a `maxlength` at least as long as the matching Synthetic_Registration value, and the design SHALL list each Legacy_Field's control type, `name`, `maxlength` and `required` attribute.
6. THE Legacy_Portal registration page SHALL reproduce these eight legacy traits:
   - a table-based page layout;
   - font sizes fixed in px at 12 px or smaller for labels and body text;
   - label and body text with a contrast ratio below 4.5:1 against its background;
   - text inputs with no associated `label` element and no `aria-label`, `aria-labelledby`, `title` or `placeholder` attribute;
   - abbreviated labels in the neighbouring table cell;
   - a required consent checkbox whose explanation sits in a different table row and is not associated with the checkbox;
   - a single free-text date box (a text input, not a date input) that shows its expected format only as an abbreviation;
   - a reset button directly after the submit button in the same table cell, with no other control between them.
7. THE Legacy_Portal SHALL write all visible text in Malay, except the English part of the banner in criterion 1.2, and SHALL set `lang="ms"` on the `html` element of every Legacy_Portal document. All Malay strings SHALL be held in one content file that the design names and that the README lists as the only non-English content outside the interface locale files.
8. WHEN the registration page loads, THE Legacy_Form SHALL render with no value in any Legacy_Field: every text input empty, no gender radio option selected, every select on an option with an empty value, and the consent checkbox unchecked.
9. WHILE scripts are disabled in the browser, THE Legacy_Portal SHALL let the user go from the home page to the registration page, submit the Legacy_Form and reach the Legacy_Handler response, using only HTML links, HTML forms and server responses, with no script on any Legacy_Portal document.
10. IF the Worker receives a GET request for a path under `/legacy/` that criterion 1.1 does not list, THEN THE Worker SHALL return a not-found document that carries the banner of criterion 1.2, contains no form controls and links only to `/legacy/`.

### Requirement 2: Legacy handler

**User Story:** As a user, I want the legacy portal's own handler to process my registration, so that the revived page provably uses the original backend.

#### Acceptance Criteria

1. WHEN the Legacy_Handler receives a `POST /legacy/register` request whose body passes its validation, THE Legacy_Handler SHALL return a confirmation response written in Malay that contains a Reference_Number, a statement that the registration is received and is not an appointment confirmation, the Received_Fields_Summary, and a link to the FormBridge clinic PDF flow. The Received_Fields_Summary SHALL list exactly the eight Legacy_Fields of Requirement 1.5, with no entry for the submit button or the reset button.
2. THE Legacy_Handler SHALL validate a submission with its own legacy rules: every Legacy_Field marked `required` in the Legacy_Form appears exactly once and has at least one non-whitespace character; the consent value equals the consent checkbox's `value` attribute; the gender value equals one of the Legacy_Form's radio values; no value is longer than the Legacy_Field's `maxlength`, counted the same way the browser counts `maxlength`; and the body contains no field name that is absent from the Legacy_Form and no field name more than once.
3. IF a submission fails the Legacy_Handler validation, THEN THE Legacy_Handler SHALL return a legacy-style error page in Malay that names every failing Legacy_Field by its `name` attribute in a single response, gives a link back to `/legacy/register`, contains no Reference_Number, and repeats no submitted value and no field name that is absent from the Legacy_Form.
4. THE Legacy_Handler SHALL record each value in the Received_Fields_Summary exactly as received, with no trimming, case change or normalization, so that two submissions with identical bodies produce identical Received_Fields_Summaries whether the body comes from the Legacy_Form directly or from the Mirror.
5. THE Legacy_Handler SHALL keep submitted values only for the duration of the request, with no write to any storage, cache, log or analytics service, and SHALL return in each response no value from any other request.
6. THE Worker SHALL send every Legacy_Portal response with `Cache-Control: no-store`.
7. THE Legacy_Handler SHALL read submitted values only from the request body and SHALL ignore query-string parameters on `POST /legacy/register`, leaving them out of the validation and the Received_Fields_Summary. THE Legacy_Portal SHALL keep submitted values out of every URL, redirect target and response header.
8. IF a request to `/legacy/register` uses a method other than GET or POST, or a POST body is not a URL-encoded form body (the HTML form default), or a POST body is larger than 16 KB (16,384 bytes), THEN THE Worker SHALL reject the request with the shared error shape before the Legacy_Handler runs, and SHALL issue no Reference_Number.
9. THE Legacy_Handler SHALL produce a Reference_Number that matches the pattern `SR-DEMO-YYYYMMDD-NNNNNN`, where `YYYYMMDD` equals the UTC date on which the Legacy_Handler received the request, and SHALL compute the `NNNNNN` digits without using any submitted value as input.
10. THE Legacy_Handler SHALL render every value in the Received_Fields_Summary as plain text, so that a value containing markup characters such as `<`, `>`, `&` or quotes appears literally on the confirmation response and adds no element or attribute to the document.

### Requirement 3: Supported paths, methods and page versions

**User Story:** As the developer, I want the revival to accept only known pages and transitions, so that the agent cannot wander off or act on a page it does not understand.

#### Acceptance Criteria

1. THE ReForge_App SHALL define the Allow_List as one constant that lists exactly four entries, each made of an HTTP method, a path on the Worker's own origin and a response transition: GET `/legacy/` returning the home page, GET `/legacy/register` returning the registration page, POST `/legacy/register` returning a confirmation response, and POST `/legacy/register` returning an error page.
2. WHEN the Revival_Frame finishes loading a document, THE ReForge_App SHALL check the document's origin, path, the method that produced it and its page type (home page, registration page, confirmation response or error page) against the Allow_List before the Page_Extractor, the Executor or the Verifier reads the document. A path matches only when it is identical to an Allow_List path and carries no query string.
3. IF the Revival_Frame loads a document whose origin, path, method or page type has no matching Allow_List entry, or whose page type cannot be determined, THEN THE ReForge_App SHALL stop the agent loop, perform no further Actions, keep the answers already given in memory for the session, and show the user a message in the Interface_Language that the page is not supported, with a control that reloads the registration page.
4. THE design SHALL record the supported Page_Version of the home page and of the registration page, both computed from the sanitised HTML that the Worker serves for the GET request. A test SHALL fail when the Page_Version of either served page differs from its recorded value. Confirmation responses and error pages carry per-submission content and SHALL have no recorded Page_Version.
5. WHEN the Page_Version of the loaded registration page differs from the recorded supported Page_Version, THE Mirror SHALL show a notice in the Interface_Language on every Mirror screen that the page has changed since it was tested, and THE ReForge_App SHALL use no Precomputed_Page_Plan whose Page_Version differs from the loaded Page_Version.
6. WHILE the agent loop is active, IF the Revival_Frame loads an Allow_List document that does not match the current stage (any document other than the registration page during the question flow and the review screen, or any document other than a POST `/legacy/register` response after the user confirms), THEN THE ReForge_App SHALL stop the agent loop, perform no further Actions, and show the user the message and reload control described in criterion 3.3. A reload of the registration page that the ReForge_App itself starts under criterion 3.3, Requirement 10.9 or Requirement 12.6 SHALL count as an expected transition and SHALL NOT stop the agent loop.
7. THE test suite SHALL include automated tests that load into the Revival_Frame a path outside the Allow_List, an Allow_List path with a query string, and the home page during the question flow, and SHALL assert in each case that the agent loop stops, no Action runs, the Legacy_Form is not submitted and the "page is not supported" message appears.

### Requirement 4: Sanitisation, content security and navigation limits

**User Story:** As the developer, I want the legacy pages isolated and stripped of anything active, so that page content cannot run code, leak data or steer the agent.

#### Acceptance Criteria

1. THE Worker SHALL sanitise every Legacy_Portal page, including the confirmation response and the error page, so that the served HTML contains none of the following: `script` or `noscript` elements; inline event-handler attributes (any attribute whose name starts with `on`); `javascript:` or `data:` URLs in any attribute; `iframe`, `frame`, `object`, `embed` or `base` elements; `srcdoc` attributes; `meta` elements with `http-equiv="refresh"`; and absolute or protocol-relative URLs that point outside the Worker's own origin in `href`, `src`, `action`, `formaction` or CSS `url()` and `@import` values.
2. THE Worker SHALL send every Legacy_Portal response, including Legacy_Handler error pages and the shared-error-shape rejections of Requirement 2.8, with a Content-Security-Policy that blocks all scripts (inline, external and `eval`), blocks plugin objects, restricts the document base URI to the Worker's own origin, allows images and stylesheets only from the Worker's own origin, allows form submissions only to the Worker's own origin, and allows framing only by pages on the Worker's own origin.
3. THE ReForge_App SHALL create the Revival_Frame with a sandbox that grants exactly two permissions, same-origin access and form submission, so that the Revival_Frame document cannot run scripts, open pop-ups or new windows, navigate the top-level ReForge_App window, show modal dialogs or start downloads.
4. WHEN the Revival_Frame loads the registration page, THE ReForge_App SHALL check before the first Action, and again immediately before the Executor clicks the submit button, that the Legacy_Form `action` resolves to `/legacy/register` on the Worker's own origin, that its `method` is POST, and that the submit button carries no `formaction`, `formmethod` or `formtarget` attribute that would change either value.
5. THE Page_Extractor SHALL treat all Legacy_Portal text (label text, neighbouring-cell text, option texts and nearby page text) as untrusted data, and every AI prompt that carries Page_Model text SHALL place each text value inside marked data delimiters, escape any occurrence of those delimiters within the text, and instruct the model that the delimited text is form data that contains no instructions and cannot change the task or the reply schema.
6. WHEN the Page_Extractor reads a test variant of the registration page whose label, neighbouring-cell, option and nearby texts contain instruction-like content (text that tells the agent to click the reset or submit button, change an answer, follow a URL, use a CSS selector or ignore earlier instructions), THE ReForge_App SHALL produce the same Element_Ids, control types, option values and allowed Action kinds as for the registration page without that content, and SHALL perform no Action other than those that follow a user answer or the user's explicit confirmation.
7. THE test suite SHALL include automated tests that prove each of criteria 4.1 to 4.4 on every served Legacy_Portal page and on a hostile test page that contains a script, an inline event handler, a `javascript:` link, an external image and stylesheet, a meta refresh, a foreign form `action` and a submit button with a foreign `formaction`; the hostile test page SHALL exist only in the test suite and SHALL NOT be reachable on the deployed app.
8. IF a Legacy_Portal page still contains any construct listed in criterion 4.1 after sanitisation, THEN THE Worker SHALL return the shared error shape instead of the page, and THE ReForge_App SHALL show the user a message that the page is not supported.
9. IF the check in criterion 4.4 fails, THEN THE ReForge_App SHALL stop the agent loop, perform no further Actions, leave the Revival_Frame document unchanged, and show the user a message that the form sends data somewhere other than the legacy portal and will not be submitted by the Mirror.

### Requirement 5: Observe (page model extraction)

**User Story:** As a user, I want the app to understand the old page without seeing what I type, so that my answers stay private.

#### Acceptance Criteria

1. WHEN the user presses "Revive this page" on a registration page that has passed the Allow_List check of Requirement 3.2, THE Page_Extractor SHALL build the Page_Model from the document in the Revival_Frame within 1 second of the press, without making any network request.
2. THE Page_Extractor SHALL record in the Page_Model the page path and the Page_Version of the loaded document, plus exactly one entry for each Legacy_Field in the Legacy_Form in document order. For the registration page this is ten entries: the eight Legacy_Fields of Requirement 1.5, the submit button and the reset button. Radio inputs that share a `name` SHALL be combined into one entry that lists every option's `value` and option text in document order.
3. THE Page_Extractor SHALL build each Element_Id only from the form, the control type and the `name` attribute (and the `value` attribute for each radio option). Loading the same Page_Version in any session SHALL produce the same set of Element_Ids, and no two entries in one Page_Model SHALL share an Element_Id except the entries that criterion 5.8 keeps and marks Do_It_Yourself.
4. THE Page_Extractor SHALL record the following evidence for each Legacy_Field:
   - `name` and `id`
   - associated label text, meaning the text of a `label` element tied to the field by `for` or by wrapping
   - neighbouring-cell text, meaning the text of the table cell directly before the field's cell in the same row
   - option values and option texts
   - `required` and `maxlength`
   - document position, as a zero-based index in Legacy_Form document order

   The Page_Extractor SHALL collapse runs of whitespace to one space and trim each text item. Any evidence item the document lacks SHALL be recorded as empty or absent, never inferred.
5. THE Page_Extractor SHALL exclude from the Page_Model every current value and default value of text inputs, the `value` attribute of text inputs, the checked and default-checked state of radios and checkboxes, the selected and default-selected state of select options, every `hidden` input with its `name` and `value`, and any text the user has typed into the Revival_Frame. This exclusion SHALL cover the label text, the neighbouring-cell text and the nearby page text as well.
6. THE Page_Extractor SHALL limit nearby page text to the visible text in the same table row as the Legacy_Field, leaving out the field's associated label text, its neighbouring-cell text and the text of any form control. The Page_Extractor SHALL keep the first 200 characters after whitespace normalisation, and SHALL truncate associated label text and neighbouring-cell text to 200 characters each.
7. FOR ALL documents that differ only in the values entered into Legacy_Fields (typed text, selected options, checked radios and checked checkboxes), THE Page_Extractor SHALL produce Page_Models that are deep-equal and serialise to identical JSON.
8. IF two Legacy_Fields in the Legacy_Form would receive the same Element_Id, THEN THE Page_Extractor SHALL keep both entries in the Page_Model, mark both Legacy_Fields Do_It_Yourself, and continue extracting the remaining Legacy_Fields.
9. IF the Legacy_Form contains a form control whose type is not one of text input, select, radio group, checkbox, submit button or reset button (other than a `hidden` input), THEN THE Page_Extractor SHALL record that control in the Page_Model with an unsupported control type and its evidence from criterion 5.4, and mark it Do_It_Yourself.
10. IF the Revival_Frame document cannot be read, contains no Legacy_Form, contains more than one form, or its Legacy_Form contains more than 50 form controls, THEN THE Page_Extractor SHALL produce no Page_Model. THE ReForge_App SHALL then send no page-analysis request, perform no Action, leave the Revival_Frame document unchanged, and tell the user in the Interface_Language that the page could not be read and can be completed directly in the Revival_Frame.

### Requirement 6: Plan (AI page analysis and plan validation)

**User Story:** As a user, I want plain questions in my language for each old field, and I want the app to refuse anything it cannot trust, so that I am never misled about what a field means.

#### Acceptance Criteria

1. WHEN the Page_Model is ready and the user has acknowledged the data notice of Requirement 13.7, THE ReForge_App SHALL send one page-analysis request, carrying the Page_Model, its Page_Version and the Interface_Language, to one Worker API route, and SHALL send no page-analysis request before that acknowledgement.
2. THE Worker SHALL obtain the Page_Plan through a page-analysis method of the AiProvider interface, implemented by both the real Workers AI provider and the deterministic mock provider, so that the route handler contains no provider-specific code.
3. THE Worker SHALL validate the page-analysis request body with a zod schema, reject an invalid body with a 400 response in the shared error shape before any AiProvider call, and apply the existing per-IP rate limit and the body-size limit set in the design.
4. IF a Page_Plan entry carries an Element_Id that is not in the submitted Page_Model, THEN THE Plan_Validator SHALL discard that entry and keep the remaining valid entries.
5. IF a Page_Plan contains more than one entry for the same Element_Id, THEN THE Plan_Validator SHALL keep the first entry in reply order and discard every later entry for that Element_Id.
6. IF a Page_Plan entry has any property other than Element_Id, human label, question, answer type and confidence, a human label outside 1 to 80 characters, a question outside 1 to 200 characters, a human label or question that contains HTML markup or a URL, or a confidence outside 0.0 to 1.0, THEN THE Plan_Validator SHALL discard that entry, so that no CSS selector, XPath, script, URL or Action passes to the Mirror or the Executor.
7. THE Plan_Validator SHALL accept an answer type only when the answer type is compatible with the Legacy_Field's control type: a text input accepts `text`, `ic`, `phone`, `postcode`, `date`, `email` or `description`; a select accepts `dropdown`; a radio group accepts `radio`; a checkbox accepts `checkbox`.
8. IF a Page_Plan entry carries an answer type that is incompatible with the control type, THEN THE Plan_Validator SHALL replace it with the implied type (`text` for a text input, `dropdown` for a select, `radio` for a radio group, `checkbox` for a checkbox) and set the entry's confidence to 0.
9. WHEN the Mirror presents a select or radio group question, THE Mirror SHALL offer exactly the options listed for that Legacy_Field in the Page_Model, and THE Executor SHALL write the Page_Model option value of the chosen option, whatever option text the Mirror shows.
10. IF the page-analysis reply fails schema validation, or an attempt gets no reply within 20 seconds, THEN THE Worker SHALL retry once with the same input. IF the retry fails schema validation, THEN THE Worker SHALL return the Heuristic_Extractor result and report Analysis_Mode `heuristic`. Timeout, quota and rate-limit failures continue as Requirement 7.2 and 7.3 describe.
11. WHEN a Page_Plan entry has a confidence below 0.7, THE Mirror SHALL show the original legacy label, the neighbouring-cell text and the nearby page text, and SHALL ask the user to accept or decline the proposed question before an answer input is shown. IF the user declines, THEN THE Mirror SHALL mark that Legacy_Field Do_It_Yourself.
12. THE Plan_Validator SHALL mark Do_It_Yourself every Legacy_Field other than the submit button and the reset button that has no valid Page_Plan entry after criteria 6.4 to 6.8, so that every such Legacy_Field in the Page_Model ends up either mapped or Do_It_Yourself. The submit button and the reset button SHALL be handled only by criterion 6.13.
13. THE ReForge_App SHALL identify the submit button and the reset button from the Page_Model by control type alone, and SHALL ignore any human label, question, answer type or confidence the Page_Plan gives for either button.
14. WHILE the Analysis_Mode is `live`, `mock` or `cached`, THE Mirror SHALL label every Page_Plan question and human label as machine-translated in the Interface_Language.
15. IF the page-analysis request returns an error response or gets no response within 45 seconds, THEN THE Mirror SHALL tell the user in the Interface_Language that the page could not be analysed, perform no Action, leave the Revival_Frame document unchanged, and offer a retry control and the option to fill in the legacy page directly.
16. IF the Page_Model contains no submit button or more than one, THEN THE ReForge_App SHALL mark the submission step Do_It_Yourself and tell the user to submit the Legacy_Form directly in the Revival_Frame after the review screen.

### Requirement 7: Analysis modes and their disclosure

**User Story:** As a user, I want to know whether live AI, simulated answers or saved analysis produced the questions, so that I can judge how far to trust them.

#### Acceptance Criteria

1. WHILE `AI_MODE` is not set to `real` or the Workers AI binding is absent, THE Worker SHALL produce the Page_Plan with the deterministic mock provider, make no call to Workers AI, and return Analysis_Mode `mock` in the page-analysis response. The mock provider SHALL return an identical Page_Plan for identical Page_Model and Interface_Language inputs.
2. IF a live page-analysis call fails with a quota, rate-limit, timeout or other provider error after every attempt that Requirement 6.10 allows, and a Precomputed_Page_Plan exists whose Page_Version and Interface_Language both match the request, THEN THE Worker SHALL pass that Precomputed_Page_Plan through the Plan_Validator against the submitted Page_Model, return the validated result, and return Analysis_Mode `cached` in the page-analysis response.
3. IF a live page-analysis call fails with a quota, rate-limit, timeout or other provider error after every attempt that Requirement 6.10 allows, and no Precomputed_Page_Plan matches both the Page_Version and the Interface_Language, THEN THE Worker SHALL return the Heuristic_Extractor result and return Analysis_Mode `heuristic` in the page-analysis response. THE Worker SHALL return Analysis_Mode `heuristic` in the same way when Requirement 6.10 substitutes the Heuristic_Extractor result after two schema-validation failures.
4. THE Heuristic_Extractor SHALL make no network request and SHALL produce an identical Page_Plan for identical Page_Models. It SHALL set every confidence to 0 and build each question as a fixed Interface_Language sentence from the locale files that quotes the original legacy label and neighbouring-cell text unchanged, with that quoted text marked as Malay through a `lang` attribute. It SHALL derive the answer type of a select, radio group or checkbox from the control type alone. It SHALL give a text input a type other than `text` only when the field's `name`, `maxlength` or option evidence matches a rule listed in the design.
5. WHILE a Page_Plan is in use, THE Mirror SHALL show on every Mirror screen, above the current question or result and before any input in reading order, a text notice in the Interface_Language that names the Analysis_Mode returned in the page-analysis response. Each mode has its own notice: `live` says that AI wrote the questions; `mock` says that the questions are simulated demonstration output and no AI analysed the page, and the existing Demo mode banner is also shown; `cached` says that the questions come from an analysis saved when the page was tested and no live AI call was made; `heuristic` says that no AI was used and the questions quote the original legacy labels.
6. THE ReForge_App SHALL generate Precomputed_Page_Plans only through one named script that runs the real provider for the supported Page_Version and for each Interface_Language listed in the design, including at least `en` and `zh-Hans`. The script SHALL validate each reply with the shared schema and the Plan_Validator, and write each passing result keyed by Page_Version and Interface_Language. For any reply that fails validation, the script SHALL write nothing for that key and exit with a non-zero status.
7. WHEN the user changes the Interface_Language after analysis, THE ReForge_App SHALL keep the Element_Ids, answer types, confidences, Do_It_Yourself statuses, entered answers, Intended_Values and current step unchanged, and SHALL replace only the human labels and questions. In `live` and `mock` modes it gets the new text from a re-translation request that carries only the existing human labels, the existing questions and the new Interface_Language. In `cached` mode it uses the Precomputed_Page_Plan for the new Interface_Language when one matches the Page_Version. In `heuristic` mode it rebuilds the questions from the locale files without a network request.
8. WHEN the Workers AI binding is present, `AI_MODE` is set to `real`, and the live page-analysis reply passes schema validation within the attempts that Requirement 6.10 allows, THE Worker SHALL return that Page_Plan and Analysis_Mode `live` in the page-analysis response.
9. IF a re-translation request fails, returns a reply that fails schema validation, or gets no reply within the 20-second per-attempt timeout that Requirement 6.10 sets, or IF `cached` mode has no Precomputed_Page_Plan for the new Interface_Language, THEN THE Mirror SHALL keep the human labels and questions in the previous language with their `lang` attribute set to that language, keep every answer, and show a notice in the new Interface_Language that the questions could not be translated.

### Requirement 8: Act (validated actions in the revival frame)

**User Story:** As a user, I want to watch the old page fill in as I answer, so that I can see the app operating the original site.

#### Acceptance Criteria

1. THE Executor SHALL accept only Actions of kind `fill`, `select`, `check` or `click`, each addressed by an Element_Id from the current Page_Model, where the kind matches the Legacy_Field's control type as follows: `fill` for a text input, `select` for a select, `check` for a checkbox or one radio option, and `click` for the submit button. A `fill` or `select` Action carries one value. A `check` Action on a checkbox carries a checked or unchecked state, and a `check` Action on a radio option sets that option checked, except the clearing Action of criterion 8.11, which carries the unchecked state.
2. IF the Executor receives an Action with any other kind, an Element_Id not in the current Page_Model, a kind that does not match the Legacy_Field's control type, a `fill` value longer than the Legacy_Field's `maxlength`, or a `select` value not among the Legacy_Field's option values in the Page_Model, or receives any Action while the Page_Version of the document in the Revival_Frame differs from the Page_Version in the current Page_Model, THEN THE Executor SHALL reject the Action and leave every Legacy_Field value, checked state and selected state in the Revival_Frame document unchanged.
3. THE Executor SHALL locate each Legacy_Field in the Revival_Frame document by the form, control type and `name` (and radio `value`) that the Element_Id encodes, without any selector or locator supplied by the AI service.
4. WHEN the user moves past a mapped question in the Mirror with an answer that passes validation, THE Executor SHALL write the Intended_Value into the matching Legacy_Field in the Revival_Frame within 500 ms. For a text input it sets the value through a `fill` Action, for a select it selects the option whose value equals the Intended_Value through a `select` Action, for a radio group it checks the option whose value equals the Intended_Value through a `check` Action on that option, and for a checkbox it sets the checked state through a `check` Action.
5. WHEN the Executor writes a Legacy_Field, THE ReForge_App SHALL scroll that Legacy_Field into view in the Revival_Frame and outline it for between 1 and 3 seconds, with an outline at least 3 CSS px thick and a contrast of at least 3:1 against the adjacent colours. The outline SHALL change no Legacy_Field value, checked state or selected state.
6. IF a `click` Action targets any Legacy_Field other than the submit button identified in Requirement 6.13, or targets the submit button before the user presses the confirm button on the review screen, THEN THE Executor SHALL reject the Action without changing the Revival_Frame document.
7. IF the consent question in the Mirror is unticked, THEN THE Executor SHALL keep the consent checkbox in the Revival_Frame unchecked, or set it back to unchecked, and SHALL reject any `check` Action that would set the consent checkbox to checked.
8. IF any Action targets the reset button, THEN THE Executor SHALL reject the Action and leave the reset button and every Legacy_Field value in the Revival_Frame document unchanged.
9. WHILE a Legacy_Field has status Do_It_Yourself, THE ReForge_App SHALL leave that Legacy_Field operable by the user directly in the Revival_Frame and SHALL perform no Action on it, so that any value the user enters there stays as typed.
10. IF the Executor finds zero elements or more than one element in the Revival_Frame document for an Element_Id, THEN THE Executor SHALL perform no write, THE ReForge_App SHALL set that Legacy_Field's status to Do_It_Yourself, and THE Mirror SHALL tell the user in the Interface_Language that the field must be completed directly on the legacy page.
11. WHEN the user skips a mapped question in the Mirror, THE Executor SHALL leave that Legacy_Field empty, unselected or unchecked. IF the Executor wrote a value into that Legacy_Field earlier in the session, THEN THE Executor SHALL clear that value with one Action of the kind criterion 8.1 assigns to the control type: a `fill` Action with an empty value for a text input, a `select` Action with the empty-value option for a select, or a `check` Action with the unchecked state for a checkbox or for the checked radio option.
12. WHILE `prefers-reduced-motion` is set, WHEN the Executor writes a Legacy_Field, THE ReForge_App SHALL show the outline from criterion 8.5 without animation or transition and SHALL scroll the Legacy_Field into view without smooth scrolling.

### Requirement 9: Mirror question flow and validation

**User Story:** As a user who struggles with the old page, I want one clear question at a time in my language with checks on my answers, so that I can complete the registration without guessing.

#### Acceptance Criteria

1. THE Mirror SHALL present one step per mapped Legacy_Field. Steps SHALL follow Legacy_Form document order and SHALL leave out Do_It_Yourself Legacy_Fields, the submit button and the reset button. Each step SHALL show a step indicator with the current step number and the total number of steps, a back control and a cancel control.
2. WHEN the user presses the back control, THE Mirror SHALL show the previous step with the earlier answer filled in, and SHALL keep every answer the user has given so far.
3. WHEN the user presses the cancel control on a step, THE Mirror SHALL handle the cancellation as Requirement 12.6 states.
4. THE Mirror SHALL show every Mirror string in the Interface_Language chosen on the existing language picker. The strings SHALL come from the Language_Registry locale files, and any missing key SHALL fall back to English. WHEN the user changes the Interface_Language during the question flow, THE Mirror SHALL keep the current step and every answer already given.
5. WHEN the user presses the next control on a step, THE Mirror SHALL validate the answer through the existing Country_Pack validation entry point with the `MY` country pack. The rules SHALL be: IC number, phone number and postcode by the `MY` rules; email by the shared rules; and a blank answer rejected when the Legacy_Field carries the `required` attribute in the Page_Model. THE Mirror SHALL move to the next step only when the answer passes.
6. IF an answer fails validation, THEN THE Mirror SHALL keep the user on the same step with the typed answer still in the input. THE Mirror SHALL show the Country_Pack error message in the Interface_Language below the input, linked to the input with `aria-describedby` and announced through an `aria-live="polite"` region. THE Mirror SHALL leave the matching Legacy_Field in the Revival_Frame unchanged.
7. THE Mirror SHALL ask for the date of birth as three inputs: day (1 to 31), month (1 to 12) and year (4 digits). THE Mirror SHALL state the date format that the Legacy_Form expects and SHALL reject a combination that is not a real calendar date through the existing date validation. THE Mirror SHALL write the date in the Legacy_Form's format as a Documented_Transformation. IF the Page_Model text near the date field states no date format, or states more than one, THEN THE Mirror SHALL ask the user to choose one of the date formats the existing date validation supports before writing the date.
8. THE Mirror SHALL ask the consent question as one checkbox that starts unticked, with the full consent statement in the Interface_Language and the original legacy wording available on request. IF the user leaves the consent checkbox unticked, THEN THE Mirror SHALL leave the legacy consent checkbox unchecked, show the consent question with a message that registration needs consent, and keep the confirm button on the review screen unavailable.
9. IF the Intended_Value of a text answer is longer than the Legacy_Field's `maxlength`, counted in Unicode code points after normalization, THEN THE Mirror SHALL reject the answer with a message that states the maximum length, and SHALL keep the answer exactly as typed with no truncation.
10. THE Mirror SHALL write names, IC numbers, phone numbers, postcodes and the reason for visit without translation. The only changes allowed between the typed answer and the Intended_Value SHALL be the normalization of the existing Country_Pack validators (removal of surrounding spaces, removal of IC separators, the `MY` phone grouping) and the date Documented_Transformation.
11. THE design SHALL list every Documented_Transformation, including each Country_Pack normalization that criterion 9.10 allows. FOR ALL valid answers, THE Intended_Value SHALL equal the listed transformation of the answer.
12. WHERE a Legacy_Field has no `required` attribute in the Page_Model, THE Mirror SHALL offer a skip control on its step. WHEN the user presses the skip control, THE Executor SHALL leave that Legacy_Field empty, unselected or unchecked in the Revival_Frame, clearing any value it wrote earlier as Requirement 8.11 states, and THE Mirror SHALL record the Legacy_Field's status as `skipped`.

### Requirement 10: Verify, review, confirm and submit once

**User Story:** As a user, I want to check every value before anything is sent, and I want the app to stop if the old page shows something different, so that nothing is submitted wrongly or twice.

#### Acceptance Criteria

1. WHEN the Executor writes a Legacy_Field, THE Verifier SHALL read that Legacy_Field back from the Revival_Frame before the Mirror shows the next step. It SHALL compare the read-back with the Intended_Value by exact character-for-character equality, with no trimming, case folding or Unicode normalization. The read-back is the `value` for a text input, the selected option value for a select, the `value` of the checked option (or none) for a radio group, and the checked state for a checkbox.
2. IF a read-back value differs from the Intended_Value, including during the re-read in criterion 10.6, THEN THE ReForge_App SHALL stop the agent loop and perform no further Actions. It SHALL keep every answer the user has given, and SHALL show the original legacy label, the Intended_Value and the read-back value of each Legacy_Field that differs.
3. FOR ALL pairs of Intended_Values and read-back values, THE Verifier SHALL report a mismatch exactly when the two values differ under the comparison rule in criterion 10.1.
4. WHEN the user completes the last mapped question step, THE Mirror SHALL show a review screen. The screen SHALL list every Legacy_Field except the submit and reset buttons, in Legacy_Form document order. Each entry SHALL show the original legacy label, the question asked, the Intended_Value and exactly one status: `filled` (written, with a read-back equal to the Intended_Value), `skipped` (mapped but without a valid answer), or `do it yourself` (status Do_It_Yourself).
5. WHEN the user edits an answer from the review screen, or re-enters an answer for a Legacy_Field flagged under criterion 10.2, THE Mirror SHALL re-validate the answer, update the Legacy_Field through the Executor and repeat the Verifier read-back. The agent loop SHALL resume for that Legacy_Field only when the new read-back equals the Intended_Value.
6. WHEN the user presses the confirm button on the review screen, THE Verifier SHALL re-read every mapped Legacy_Field, and THE Executor SHALL click the submit button once, and only if every read-back value equals its Intended_Value.
7. WHILE a submission is in progress (from the submit click until an allowed response loads in the Revival_Frame or the 15-second timeout in criterion 10.8 expires), or after a confirmation response has been received in the current revival, THE Mirror SHALL disable the confirm button and THE Executor SHALL reject any further `click` Action on the submit button.
8. IF no allowed response loads in the Revival_Frame within 15 seconds after the submit click, THEN THE Mirror SHALL tell the user that the result is unknown and ask the user to check the legacy page in the Revival_Frame. It SHALL keep every answer, warn that submitting again may create a second registration, and allow a resubmission only after a new press of the confirm button.
9. WHEN the Revival_Frame loads the Legacy_Handler error page, THE Mirror SHALL show the original legacy label of each Legacy_Field the Legacy_Handler named, keep every answer, and open the question for the first named Legacy_Field in document order. Because the error page replaces the registration document, THE ReForge_App SHALL reload the registration page in the Revival_Frame (an expected transition under Requirement 3.6), and THE Executor SHALL write every mapped Legacy_Field again from the kept answers, each with a read-back equal to its Intended_Value, before the confirm button becomes available. A new submission SHALL require a new press of the confirm button.
10. WHEN the Revival_Frame loads a confirmation response, THE Verifier SHALL read the Reference_Number and the Received_Fields_Summary from the Revival_Frame document. It SHALL compare the received value of each Legacy_Field with status `filled` against its Intended_Value, using the equality rule in criterion 10.1. A checked checkbox matches when the summary contains that checkbox's own `value`. Legacy_Fields with status `skipped` or Do_It_Yourself SHALL be left out of the comparison.
11. WHEN every compared received value equals its Intended_Value and the Reference_Number matches the pattern `SR-DEMO-YYYYMMDD-NNNNNN`, THE Mirror SHALL report a verified completion with the Reference_Number.
12. IF any compared received value differs from its Intended_Value, or a Legacy_Field with status `filled` is missing from the Received_Fields_Summary, or the summary contains a field name that is not in the Page_Model, or the Reference_Number is absent or does not match its pattern, THEN THE Mirror SHALL report that the submission could not be verified, list each difference by original legacy label, and perform no automatic resubmission.
13. WHILE any Verifier read-back is pending or any mapped Legacy_Field has a read-back value that differs from its Intended_Value, THE Mirror SHALL keep the confirm button disabled and state the reason in the Interface_Language.

### Requirement 11: Report and confirmation in the user's language

**User Story:** As a user, I want the result in my language with the original available, so that I understand what happened and can show the original if asked.

#### Acceptance Criteria

1. WHEN the Mirror reports a verified completion, THE Mirror SHALL show a confirmation screen in the Interface_Language that states that the registration was received and that the registration is not an appointment confirmation, and shows the Reference_Number character for character as the Verifier read it from the confirmation response. These strings SHALL come from the Language_Registry locale files, not from the AI service.
2. WHEN the user activates the "show original" control on the confirmation screen, THE Mirror SHALL show the original confirmation text that the Verifier read from the confirmation response document in the Revival_Frame, unchanged, inside an element whose `lang` attribute is set to Malay (`ms`). The Interface_Language confirmation SHALL stay visible.
3. WHEN the user activates the "show original" control a second time, THE Mirror SHALL hide the original confirmation text, keep the Interface_Language confirmation and the Reference_Number visible, and leave keyboard focus on the control.
4. WHEN the Mirror shows a result (verified completion, a submission that could not be verified, or an unknown outcome), THE Mirror SHALL list every Legacy_Field with status `skipped` or Do_It_Yourself, giving its original legacy label and its status. IF no Legacy_Field has either status, THEN THE Mirror SHALL state in the Interface_Language that every field was filled.
5. THE Mirror confirmation screen SHALL offer a link that opens the FormBridge flow with the clinic registration PDF fixture loaded and the Interface_Language unchanged. The link SHALL carry no answer value from the Mirror in its URL, and the FormBridge flow SHALL start with every field empty.
6. THE Legacy_Portal confirmation response SHALL show, in Malay, a link to the same FormBridge clinic PDF flow for users who submitted the Legacy_Form directly.
7. IF the Verifier cannot read the original confirmation text from the confirmation response document, THEN THE Mirror SHALL state in the Interface_Language that the original text is unavailable, SHALL show no substitute or reconstructed Malay text, and SHALL still show the Reference_Number if the Verifier read one that matches its pattern.

### Requirement 12: Human control and honest automation

**User Story:** As a user, I want to stay in charge of every step, so that the app never acts for me without my say.

#### Acceptance Criteria

1. THE ReForge_App SHALL trigger a submission of the Legacy_Form only from a press of the confirm button on the review screen, and SHALL trigger no submission from any other event, including pressing Enter in a Mirror input, answering the last question, reaching the review screen, changing the Interface_Language, receiving a Page_Plan, or the end of a timeout.
2. WHEN a Legacy_Field receives status Do_It_Yourself, because it has no valid Page_Plan entry, shares an Element_Id with another Legacy_Field, or the Executor cannot locate it or rejects its Action, THE Mirror SHALL show that Legacy_Field with its original legacy label (with a `lang` attribute set to Malay), a plain-language reason in the Interface_Language, and a control that scrolls the Revival_Frame to that Legacy_Field and highlights it.
3. THE Mirror SHALL show each Do_It_Yourself Legacy_Field on the review screen with status `do it yourself` and no value, and SHALL neither propose a value for it nor write one into it.
4. WHILE the user is on a Mirror screen and the viewport is at least 1024 CSS px wide, THE ReForge_App SHALL keep the Revival_Frame visible beside the Mirror. WHILE the viewport is narrower than 1024 CSS px, down to 360 CSS px, THE ReForge_App SHALL offer a control that shows and hides the Revival_Frame without changing the current step or any entered answer.
5. IF the user tries to close, reload or navigate away from the page while at least one answer has been entered in the Mirror and no confirmation response has been received, THEN THE ReForge_App SHALL show the browser's leave-page warning before leaving, and SHALL not save the answers to any storage.
6. WHEN the user presses the cancel control in the Mirror, THE Mirror SHALL ask the user to confirm the cancellation. WHEN the user confirms, THE ReForge_App SHALL stop the agent loop, perform no further Actions, submit nothing, discard the Mirror answers from memory, and reload the registration page in the Revival_Frame so that every Legacy_Field is in the initial state of Requirement 1.8, with every text input empty and the consent checkbox unchecked. WHEN the user declines, THE Mirror SHALL return to the same step with every answer kept.
7. THE Mirror SHALL give a Legacy_Field status `filled` only when the Verifier's most recent read-back of that Legacy_Field equals its Intended_Value, and SHALL show every other mapped Legacy_Field as `skipped` or as the mismatch reported under Requirement 10.2.
8. IF a Do_It_Yourself Legacy_Field carries the `required` attribute in the Page_Model and is empty in the Revival_Frame when the user reaches the review screen, THEN THE Mirror SHALL name that Legacy_Field in a notice telling the user to complete it in the Revival_Frame before confirming, and SHALL leave the confirm button available.

### Requirement 13: Privacy

**User Story:** As a user, I want my answers to go only to the portal I am registering with, so that nothing else sees my personal data.

#### Acceptance Criteria

1. THE ReForge_App SHALL send to the page-analysis route only the Page_Model (which carries the page path and the Page_Version) and the Interface_Language, and SHALL send to the re-translation route of Requirement 7.7 only the existing human labels, the existing questions and the target Interface_Language.
2. THE Worker SHALL send to the AI service only Page_Model content, the existing human labels and questions, the Interface_Language and fixed prompt text, and SHALL tag all Legacy_Portal text in the prompt as untrusted form data as Requirement 4.5 states.
3. THE ReForge_App SHALL send the user's answers, raw or normalized, in exactly one kind of request: the Legacy_Form POST body to the Legacy_Handler, sent only after the user's explicit confirmation on the review screen. No other request to the Worker or to any other origin SHALL carry an answer.
4. THE ReForge_App SHALL keep answers in memory for the lifetime of the current page load only. It SHALL write no answer to localStorage, sessionStorage, IndexedDB, cookies or service worker caches, and SHALL discard all answers when the user presses the cancel control and confirms the cancellation, reloads the page or closes the tab.
5. THE Worker SHALL write log entries for page-analysis, re-translation and Legacy_Portal requests that contain only these items: request id, route, status, duration, error code, Analysis_Mode, model, attempts, token counts, neurons and cache flag. No log entry SHALL contain a request body, prompt, model reply, Page_Model text, human label, question, answer, Legacy_Field name or any part of a Received_Fields_Summary.
6. THE Worker SHALL write error messages and error details that name only schema paths or Legacy_Field names and that contain no submitted value.
7. WHEN the user presses "Revive this page", THE Mirror SHALL show a data notice in the Interface_Language before any page-analysis request is sent, and SHALL show the notice again on the review screen. The notice SHALL state four things: labels and nearby text from the legacy page go to the AI service; on a language change, the existing labels and questions go to the AI service for re-translation; answers stay in the browser until the user confirms; confirmed answers go only to the legacy portal's own handler.
8. IF the user has not acknowledged the data notice, THEN THE ReForge_App SHALL send no page-analysis or re-translation request and SHALL leave the Legacy_Form operable directly in the Revival_Frame.
9. THE data notice text SHALL be present in the locale file of every core language in the Language_Registry, and SHALL fall back to English for any experimental language that lacks the key.
10. THE test suite SHALL include canary tests that use two unique canary values. The first is typed into a Legacy_Field in the Revival_Frame before extraction. The second is entered as an answer in the Mirror and carried through to confirmation. The tests SHALL prove that both values are absent from the Page_Model, the page-analysis request body, the re-translation request body, the prompt sent to the AI service, every Worker log entry, every error response, localStorage, sessionStorage, IndexedDB, cookies, every request URL, and the FormBridge link URL. The second value SHALL appear only in the Legacy_Form POST body.
11. THE ReForge_App SHALL make real AI calls only from the named Precomputed_Page_Plan generation script and the model measurement script, each run only with `AI_MODE` set to `real`, and from Smoke_Tests. The Smoke_Tests SHALL include the deployed acceptance run of Requirement 16.2, which the developer runs on purpose against the deployed public URL. No Smoke_Test SHALL run in CI or in the default test command, and every other automated test SHALL use the mock provider.

### Requirement 14: Accessibility of the Mirror

**User Story:** As an older user or a user of assistive technology, I want the revived page to work with a keyboard, a screen reader and large text, so that the revival removes the old barriers.

#### Acceptance Criteria

1. THE Mirror SHALL use semantic HTML on every Mirror screen: exactly one `h1`, no skipped heading levels, a "Skip to main content" link as the first focusable element that moves focus to the `main` landmark, `header` and `main` landmarks, a visible `label` element associated with every input (placeholder text never being the only label), required questions marked in visible text in the Interface_Language, persistent format helper text for IC number, phone number, postcode and date inputs linked with `aria-describedby`, `fieldset` with `legend` for every radio group, checkbox group and the day, month and year date inputs, and no ARIA role or attribute that repeats the native semantics of its element.
2. THE Mirror SHALL be operable with the keyboard alone: every Mirror control reachable with Tab and Shift+Tab in the visual reading order and activated with Enter or Space (arrow keys within radio groups), no keyboard trap outside an open dialog, any dialog keeping focus inside it while open and returning focus to the control that opened it on close, and a focus indicator at least 2 CSS px thick with a contrast of at least 3:1 against the adjacent background on every focused control.
3. THE Mirror SHALL meet, in every Mirror screen and in its default, hover and focus states, a contrast ratio of at least 4.5:1 for text below 18.66 px bold or 24 px regular, and at least 3:1 for larger text, input and control borders, icons that carry meaning, and focus indicators, each measured against the background directly behind it.
4. THE Mirror SHALL keep every pointer target at least 24 by 24 CSS px, and the Next, Back, confirm and "Revive this page" controls at least 44 by 44 CSS px.
5. THE Mirror SHALL render body text at no less than 16 CSS px, and at a 360 px viewport width and at 200% browser zoom on a 1280 px viewport THE Mirror SHALL show all Mirror content without horizontal scrolling of the Mirror, without overlapping or clipped text, and with long values (names, IC numbers, reasons for visit, Reference_Number) wrapped in full and never truncated.
6. THE ReForge_App SHALL set `<html lang>` to the BCP 47 tag of the Interface_Language and update it without a page reload when the user changes the Interface_Language, and SHALL set `lang` to Malay (`ms`) on every Mirror element that shows original legacy text, including the original legacy labels, neighbouring-cell text, nearby page text and the original consent wording.
7. THE Mirror SHALL convey every error, the `filled`, `skipped` and `do it yourself` statuses, the Analysis_Mode notice and the machine-translated label with visible text in the Interface_Language and an icon in addition to colour, and SHALL set `aria-invalid="true"` on an input while its validation error is shown and remove the attribute once the answer passes validation.
8. THE Playwright suite SHALL run axe with the tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` on these Mirror states, in both `en` and `zh-Hans`, and SHALL fail on any reported violation: the legacy page with the "Revive this page" control, the data notice, one step for each answer type the Legacy_Form uses, a low-confidence question showing the original evidence, a validation error shown, the review screen, the verified confirmation, the "could not be verified" report, the agent-loop stop message, the "do it yourself" report, and the larger-text option turned on.
9. THE axe checks SHALL exclude the Revival_Frame document, and THE manual accessibility checklist SHALL state that the Legacy_Portal pages fail accessibility on purpose and SHALL contain Mirror entries for a keyboard-only run of the whole revival flow, a screen-reader pass (NVDA or VoiceOver) on the question, review and confirmation screens, a 360 px width check, a 200% zoom check, a reduced-motion check and a larger-text check, each recorded with a pass or fail result and the date checked.
10. WHEN the Mirror opens after "Revive this page", the step changes, or the review screen, the confirmation, the "could not be verified" report or the agent-loop stop message appears, THE Mirror SHALL move keyboard focus to the `h1` or step heading of the new content, and screen readers SHALL announce that heading.
11. WHEN the user turns on the larger-text option in the Mirror, THE Mirror SHALL raise body text to at least 20 CSS px on every Mirror screen, keep that setting in memory only for the rest of the page load until the user turns it off, and still meet criterion 14.5 at a 360 px viewport width.
12. WHILE `prefers-reduced-motion: reduce` is set, THE Mirror SHALL change steps and screens without slide or movement animations, using no animation or a fade of 200 ms or less.

### Requirement 15: Evidence that the original backend did the work

**User Story:** As a judge, I want proof that the revived page sends the same data the old page would send, so that I can trust the claim that the original site still does the real work.

#### Acceptance Criteria

1. THE Playwright suite SHALL submit the Synthetic_Registration twice, each time in a separate browser context with the mock provider. The first submission SHALL be direct: the suite opens `/legacy/register` as a top-level page without the Mirror, types the Intended_Values for the Synthetic_Registration into the Legacy_Form and presses its submit button. The second submission SHALL go through the Mirror: the suite answers every Mirror question in the Mirror with the Synthetic_Registration answers and presses the confirm button on the review screen.
2. WHEN both submissions have returned a confirmation response, THE Playwright suite SHALL assert that the two Received_Fields_Summaries are identical: the same number of entries, in the same order, with the same field names and with values that match character for character.
3. WHEN the Mirror submission has returned a confirmation response, THE Playwright suite SHALL assert three things about its Received_Fields_Summary: it contains exactly eight entries, one for each Legacy_Field of Requirement 1.5, in Legacy_Form document order; it contains no entry for the submit button, the reset button or any other name; and each received value matches the Intended_Value for that Legacy_Field character for character.
4. THE design SHALL list a row for each of the eight Legacy_Fields of Requirement 1.5. Each row SHALL give the Synthetic_Registration answer the user gives in the Mirror, the Intended_Value, and the Documented_Transformation between them, or "none". The gender row and the consent row SHALL say "none", because the Executor writes the radio option's own `value` and the checkbox's own `value`. THE Documented_Transformations SHALL be only the Country_Pack normalizations (trimming leading and trailing whitespace, removing separators from the IC number, applying the `MY` phone grouping) and writing the date of birth in the date format the Legacy_Form states.
5. THE test suite SHALL assert, for each of the eight Legacy_Fields, one of two outcomes. For a field whose design row says "none", the received value SHALL equal the Mirror answer character for character. For any other field, the received value SHALL equal the named Documented_Transformation applied to the Mirror answer. Any other difference between a Mirror answer and its received value SHALL fail the test.
6. THE Synthetic_Registration answers given in the Mirror SHALL exercise each Documented_Transformation at least once. At least one text answer SHALL have leading or trailing whitespace, the IC number SHALL be typed with separators, the mobile number SHALL be typed in a grouping that differs from the `MY` phone grouping, and the date of birth SHALL be given as separate day, month and year answers.
7. WHEN the Mirror reports a verified completion, THE Playwright suite SHALL assert two things: the Reference_Number in the confirmation response document in the Revival_Frame matches the pattern `SR-DEMO-YYYYMMDD-NNNNNN`, and the Reference_Number the Mirror shows equals it character for character.

### Requirement 16: Acceptance scenario

**User Story:** As a judge, I want the whole revival path to run on the deployed app, so that the demo shows a real, working product.

### Requirement 17: Testing of core logic

**User Story:** As the developer, I want property-based tests on the agent's safety checks, so that bugs in plan validation, actions and verification are caught early.

#### Acceptance Criteria

1. THE test suite SHALL include a fast-check property showing that FOR ALL generated Page_Plans checked against the Legacy_Form Page_Model, the Plan_Validator output contains only entries whose Element_Id is in the Page_Model, at most one entry per Element_Id (the first one generated), only properties from the Plan_Validator's closed property set, only answer types compatible with the control type (an incompatible answer type is replaced by the control-type answer type with confidence 0), and only option values present in the Page_Model; every Legacy_Field in the Page_Model other than the submit button and the reset button is either mapped or Do_It_Yourself, with none missing and none in both states.
2. THE generator for criterion 17.1 SHALL produce Page_Plans containing each of these cases: unknown Element_Ids (including an Element_Id that differs from a valid one by a single character or by letter case), duplicate Element_Ids, incompatible answer types, option values absent from the Page_Model, extra properties carrying a CSS selector, XPath, script, URL or Action, empty Page_Plans, and fully valid Page_Plans. At least one fully valid case SHALL assert that every Legacy_Field with a valid entry is mapped, so that an output in which every Legacy_Field is Do_It_Yourself fails the property.
3. THE test suite SHALL include a fast-check property showing that FOR ALL generated Actions run on the Legacy_Form in the Revival_Frame document, the Executor accepts an Action exactly when its kind is one of `fill`, `select`, `check` or `click`, its Element_Id is in the current Page_Model, and its kind matches the Legacy_Field's control type under the mapping of Requirement 8.1. The property SHALL also show that a rejected Action leaves every Legacy_Field value, checked state and selected state unchanged, and that an accepted Action changes only the addressed Legacy_Field. The generator SHALL include kinds outside the four (including letter-case variants of the four), Element_Ids absent from the Page_Model, mismatched kind and control type pairs, and a `click` addressed to the reset button.
4. THE test suite SHALL include a fast-check property showing that FOR ALL generated pairs of Intended_Values and read-back values, the Verifier reports a mismatch exactly when the two values are not exactly equal. The generator SHALL include identical pairs, pairs that differ only in leading or trailing whitespace, pairs that differ only in letter case, pairs that differ only in Unicode normalization form, pairs where one value is empty, and pairs that differ in a single character, so that a Verifier that trims, case-folds or normalizes values fails the property.
5. THE test suite SHALL include a fast-check property showing that FOR ALL generated combinations of entered state on the Legacy_Form (text typed into each text input, a selected option, a chosen radio option, and the consent checkbox ticked or unticked), the Page_Model equals the Page_Model of the same page with no entered state, including identical Element_Ids and an identical Page_Version. The property SHALL also assert that the Page_Model of the page with no entered state has the ten entries of Requirement 5.2 (the eight Legacy_Fields of Requirement 1.5, the submit button and the reset button), so that an empty Page_Model fails the property.
6. THE test suite SHALL include a fast-check property showing that FOR ALL valid date-of-birth answers (day, month and year that the existing date validation accepts, including 29 February in leap years and the first and last day of each month), splitting the written date back into day, month and year returns the original answer, and that FOR ALL invalid day, month and year combinations (including 29 February in non-leap years, day 0, day 32 and month 13) the Mirror writes no value.
7. THE test suite SHALL include a fast-check property showing that FOR ALL valid answers to each mapped Legacy_Field, the Intended_Value equals the Documented_Transformation of the answer named for that Legacy_Field in the design (including Country_Pack normalization of IC number, phone number and postcode), and that a Legacy_Field with no listed Documented_Transformation receives the answer unchanged.
8. THE test suite SHALL include a fast-check property showing that FOR ALL text answers whose Intended_Value has a length from 0 to `maxlength` + 5 characters, the Mirror accepts the answer exactly when the Intended_Value length is at most the Legacy_Field's `maxlength`, and that a rejected answer is kept untruncated and leaves the matching Legacy_Field unchanged. The generator SHALL include lengths equal to `maxlength` and `maxlength` + 1.
9. THE test suite SHALL run every property in this requirement with at least 100 generated cases, SHALL report the fast-check seed on failure, and SHALL contain no `skip` or `only` marker on these properties. A property that cannot pass yet SHALL stay failing or be marked `todo` with the reason and the task that will fix it.
10. WHEN a fast-check property finds a bug, THE developer SHALL keep the shrunk counterexample as a regression test named after the behaviour it checks, with the fast-check seed in a comment, confirm that the regression test fails on the code before the fix, and record the catch in the Kiro usage log.

### Requirement 18: Out of scope

**User Story:** As the developer, I want the limits of this skeleton written down, so that nobody reads more into the demo than it does.

#### Acceptance Criteria

1. THE ReForge_App SHALL set the Revival_Frame source only to Legacy_Portal paths in the Allow_List on the Worker's own origin, and SHALL offer no input field, URL parameter or link that loads any other address into the Revival_Frame.
2. IF the ReForge_App is opened with a URL parameter or route that names an address outside the Legacy_Portal as the page to revive, THEN THE ReForge_App SHALL load nothing from that address and SHALL show a message in the Interface_Language stating that only the fictional demonstration portal can be revived.
3. THE ReForge_App SHALL offer no sign-in, account or saved-progress feature for the revival flow, and THE Worker SHALL expose no route that returns an earlier Legacy_Form submission.
4. WHEN the user reloads the ReForge_App or opens it in a new tab during the revival flow, THE Mirror SHALL start from the first step with no earlier answer restored, and THE Revival_Frame SHALL show the Legacy_Form with every Legacy_Field in its initial state.
5. THE README SHALL contain a scope section that names the Legacy_Portal as the only supported portal and the Legacy_Form as the only supported form, lists the Interface_Languages and the Country_Pack that the automated acceptance tests cover, marks every other Interface_Language as experimental for AccessForge, and states that real websites, cross-origin pages, login pages, CAPTCHA pages, script-driven sites and general crawling are not supported.
6. THE Mirror SHALL show a scope notice in the Interface_Language on its first screen, stating that this version of AccessForge revives only the fictional demonstration portal and its one registration form.
