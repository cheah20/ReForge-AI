# Testing rules

Tests exist to catch broken behaviour. A test that would pass on broken code is worse than no test, because it hides the gap.

## Every test asserts behaviour

- Assert the result the spec asks for: the exact value written, the exact rejection code, the exact field list. "It does not throw" or "it returns something" is not enough.
- No test that only imports a module or checks that a function exists.
- No broad try/catch in tests or code that swallows an error and returns a default.
- No stub that returns early (`return null`, `return []`) to satisfy types or make a test pass.
- Never weaken, skip or delete a failing test to get green. Fix the code. If it cannot be fixed yet, leave the test failing or mark it `todo` with the reason and the task that will fix it.

## Every fix gets a test that fails on the old code

- Write or keep the test, then check it against the old code (stash the fix and run it) when the fix is not obvious.
- Name the test after the behaviour, not after the ticket.

## Property-based tests (fast-check)

- Use them for core logic: field completeness (no field silently dropped), answer-type compatibility, snippet length and privacy, batching, validation (IC, phone, postcode, dates, MaxLen), PDF fill round trips and untouched fields.
- The generator must be able to produce the failing case: omissions, duplicates, unknown ids, incompatible types, values on both sides of a limit.
- A property must not pass trivially. If all-empty or all-rejected output would satisfy it, add a case that requires real output.
- When a property finds a bug, keep the shrunk counterexample as a named regression test, with the seed in a comment, and add a row to the usage log.

## Privacy tests

- A canary test first proves the canary is really in the input (decoded `/V`, `/DV`, page content), then proves it is absent from the whole serialized output.
- Compare two inputs that differ only in the private value, and expect identical evidence.

## Fixtures and data

- Fixtures are synthetic and generated by `scripts/create-fixtures/`. A test fails when a committed fixture differs from the generator output.
- Use `example.invalid` emails, 555-0100 to 555-0199 US numbers and the synthetic answers from the fixture specification. Never real people's data.
- Tests use the mock AI provider. A test never calls real Workers AI.

## Before a checkpoint

- `npx tsc --noEmit` is clean and `npx vitest run` passes, with no new `skip` or `only`.
- Count the tests that are `todo` and say why each one is still open.
